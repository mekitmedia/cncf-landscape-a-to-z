## AutoMQ

[AutoMQ](https://www.automq.com) is a cloud-native, stateless fork of Apache Kafka that replaces the traditional storage layer with an S3-first diskless architecture. Designed for modern cloud environments, it aims to eliminate the operational burdens and high costs associated with managing stateful Kafka brokers.

### Key Features and Architecture

The core philosophy behind AutoMQ is to [rewrite the storage layer while preserving the compute layer](https://docs.automq.com/automq/what-is-automq/overview#rewrite-storage-preserve-compute). This approach ensures 100% API compatibility with the Apache Kafka ecosystem, meaning tools like Kafka Connect, Kafka Streams, and Schema Registry work seamlessly without modifications.

AutoMQ leverages a [Shared Storage architecture](https://docs.automq.com/automq/architecture/overview#shared-storage-architecture) utilizing cloud object storage (such as AWS S3) as the primary data repository, alongside a Write-Ahead Log (WAL) on scalable block storage for high performance. This fundamentally differs from Kafka's traditional Shared Nothing architecture, which relies heavily on local disks and cross-AZ replication.

By storing data in shared cloud storage, AutoMQ can achieve:
*   **Seconds-level Elasticity**: Brokers are entirely stateless. Scaling the cluster in or out happens in seconds, as there is no need to migrate heavy partition data between nodes.
*   **Zero Cross-AZ Traffic Costs**: Traditional multi-AZ Kafka deployments incur significant cross-availability zone data transfer fees. AutoMQ bypasses this by using the cloud provider's object storage as the shared medium.
*   **Significant Cost Reductions**: AutoMQ claims up to a 10x reduction in Total Cost of Ownership (TCO), primarily by eliminating the need to over-provision local EBS volumes and reducing the standard 3x replication overhead.



### Community Perspectives

While AutoMQ is highly praised for reducing cloud storage costs and simplifying operations, community discussions (such as those on [Hacker News](https://news.ycombinator.com/item?id=37719601)) highlight the trade-offs of this architectural shift.

By replacing Kafka's storage layer with S3, the performance bottleneck shifts towards cloud object storage latency. Although AutoMQ mitigates this using a Write-Ahead Log (WAL) and aggressive caching, users with extreme, sub-millisecond latency requirements may still prefer traditional Kafka deployments on bare-metal NVMe drives. However, for the majority of standard streaming use cases, many users find the trade-off highly favorable given the substantial cost savings and operational elasticity.

### Recent Updates

The project is actively maintained on [GitHub](https://github.com/AutoMQ/automq), with the recent [1.7.4 release](https://github.com/AutoMQ/automq/releases/tag/1.7.4) introducing enhancements to the S3Stream layer, optimizations for ZGC (Z Garbage Collector) memory management, and continued improvements to their new Table Topic feature (which integrates streaming data directly into formats like Apache Iceberg).

For teams struggling with Kafka scalability or looking to reduce cloud infrastructure costs, AutoMQ offers an intriguing, API-compatible alternative worth evaluating. You can dive deeper into their design in the [official documentation](https://docs.automq.com/).
